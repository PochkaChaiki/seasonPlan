Представление реализации — **диаграмма 3 вместе с 3a–3d**. Разбиение через
нативные `ref` сохраняет полное описание без одной перегруженной схемы. Вызовы
связаны с типизированными `IOperation`/`IParameter`, а не только подписаны текстом.
Показаны значимые операции; служебные UUID/setter/DTO-mapping вызовы и внутренности
JdbcTemplate/HTTPS-клиента свёрнуты в подписанные шаги. Возвраты, не влияющие на
понимание, опущены.

**Во всех семи последовательностях есть нативные пунктирные линии жизни и
полосы исполнения у системных участников.** Полосы показывают ограниченные
сегменты обработки сообщений/`ref`, а не длительность метода или одну сессию
между несколькими HTTP-запросами. Акторы не получают длинных полос исполнения:
их нативные символы имеют фиксированный размер 40×50, расположены над
типизированными Actor линиями жизни и связаны с теми же моделями `IActor`.
Координатор, хранитель и Фея-планировщик находятся слева от системы.

## Пакеты из существующего проекта

Логический вид использует **системный обзор `01-system`** из
[существующего проекта пакетов](../packages/README.md), а не новые пакеты
ответственности по сервисам. Идентификаторы, названия и описания читаются
генератором непосредственно из [packages.xml](../packages/packages.xml).
Единственный алиас — `frontend/src` → **`frontend`**, как запрошено.

| Участник логического вида | Соответствие исходной архитектуре |
| --- | --- |
| `frontend` | `frontend/src`, React-клиент; инициирует первое сообщение |
| `api` | `com.seasonplan.lifecycle.api`, REST boundary |
| `security` | `com.seasonplan.security`, аутентификация и RBAC |
| `service` | `com.seasonplan.lifecycle.service`, совместимый фасад |
| `application` | `com.seasonplan.lifecycle.application.*`, агрегировано как в `01-system` |
| `domain` | `com.seasonplan.lifecycle.domain`, доменные объекты и ограничения |
| `persistence` | `com.seasonplan.lifecycle.persistence`, JDBC и локальные транзакции |
| `pollentree` | `com.seasonplan.lifecycle.adapter.pollentree`, существующий HTTPS-адаптер |
| `PostgreSQL` | Добавленный участник базы данных, не Java-пакет |
| `Pollen Tree` | Внешний сервис, не Java-пакет |

**В логическом виде нет акторов, `fake` и `config`.** Исходный проект пакетов
не изменён; из его системного обзора выбраны только участники взаимодействия.
`application` включает `preparation`, `pollen`, `shared` и контракты `port`,
поэтому нет отдельного участника-порта или выдуманных пакетов для отдельных
сервисов подготовки. JDBC и реальный HTTPS-адаптер показаны существующими
пакетами `persistence` и `pollentree`, не новыми слоями «ports/adapters».

Линии жизни представляют экземпляры логических подсистем, а не экземпляры
UML Package. Их классификаторы принадлежат выбранным нативным пакетам;
на логическом виде скрыты технические имена этих классификаторов, чтобы
заголовки содержали только названия частей системы. В модели реализации
сервисы сгруппированы под агрегатом `application`, как в системном обзоре.

## Требования и граница с текущим кодом

Основания: [UC-3](../../../arch_docs/USE_CASE_SPECIFICATION.md),
[SRS](../../../arch_docs/SYSTEM_REQUIREMENTS_SPECIFICATION.md),
[Vision](../../../arch_docs/VISION.md),
[ST-00](../ST-00-specification-resolution.md),
[граница Древа](../POLLEN_TREE_EXTERNAL_SERVICE.md), исходники и конфигурация.
ST-00 разрешает противоречия старых требований: резерв — `CONFIRMED`,
жизненный цикл содержит ровно восемь статусов. UC-3 ограничен
**APPROVED → RITUAL_READY**; запуск RitualSession относится к UC-4.

Это **целевой проект с привязкой к текущему коду**. `«проект»` на сообщении
или объекте обозначает отсутствующий контракт либо изменяемую обвязку:

- Существующий `calculateChecklist` требует непустые задачи `READY`, хотя
  нормативная готовность требует завершения обязательных задач. Целевое
  расширение заменяет этот предикат: каталог категорий и ролей (включая
  `RITUAL_LEAD`), `COMPLETED` обязательных работ, подтверждения с датой,
  отсутствие конфликтов/CRITICAL, дополнительные условия утверждения и
  ожидающая замена ресурса. `SeasonReadinessPolicy.evaluate(...)` — проектируемый
  контракт, не существующий класс. Ручная отметка не обходит вычисляемое правило.
- Сейчас `validateRequiredRoles` фактически проверяет любое подтверждённое
  назначение, а не покрытие каталога ролей. Расписание проверяется при создании
  `CONFIRMED` и только в пределах одного плана; межсезонная проверка и повторная
  проверка при готовности требуют доработки.
- `ParticipationService.confirmParticipation(...)` — проектируемая команда:
  нынешний API принимает `CONFIRMED` от координатора, не хранит `confirmedAt`
  и не предоставляет самостоятельного подтверждения. В проектной ветви
  конфликт прекращает взаимодействие **до** сохранения подтверждения.
- `PollenService.requestAmendment(...)` и одноимённое расширение REST-клиента —
  проектируемые операции единой pollen-границы. Древо создаёт связанный `DRAFT`,
  старый `CONFIRMED` неизменяем; неподтверждённая замена блокирует готовность,
  отклонённая сохраняет прежний подтверждённый резерв. Текущий
  `requestReservation` использует `int` и не реализует связь/supersession;
  целевые граммы — `BigDecimal`, scale 3. Прямых записей пыльцы в PostgreSQL нет.
- `JdbcCommandTransaction.execute` существует, но подготовка его не вызывает.
  Целевая обвязка UC-3 объединяет локальные состояние и аудит (и outbox, когда
  требуется уведомление); ошибки имеют явные попытки записи и rollback,
  успешный ответ — только после commit. Древо не входит в эту транзакцию.
  Удалённое принятое решение нельзя «откатить» локальным rollback: нужен
  повтор идемпотентного `appendOnce`/восстановление, отмеченные на 3a.
- `updateTask` сейчас не проверяет APPROVED/начатость и не пишет аудит;
  `completeItem` также не пишет аудит. Эти изменения отмечены, а не выданы за
  реализованные. `PreparationService` допускает хранителя, но API/ST-00 дают
  переход только координатору; проектная проверка должна совпадать с API.
- Уведомления FR-88/89, доступность исполнителей, каталог, доказательства и
  расширенная политика требуют дальнейшей реализации. Проверка моделей не
  сертифицирует готовность backend к эксплуатации.

Покрытие: FR-10/13 — переход и аудит; FR-14–18 — ресурс; FR-24–34 — задачи и
назначения; FR-35–40 — готовность; FR-78–81 — неизменяемый аудит. FR-90 и запуск
ритуала намеренно оставлены UC-4. Исправление стратегических параметров по
замечанию Феи-планировщика проходит отдельные UC-1/UC-2, не меняет APPROVED тайно.

## Проверка и воспроизведение

[validation.json](validation.json) содержит результат, количества и SHA-256
доставленного VPP. Проект сохранён, его **копия открыта в другом процессе VP**;
проверены нативные типы, методы/параметры, концы сообщений, геометрия линий жизни
и компактных символов акторов, принадлежность полос исполнения и их связи с
сообщениями, исходные пакеты и первый запрос `frontend`, операнды и вложенный
`break`, ссылки `ref`, условия и непустые зарегистрированные
заметки. PNG/SVG выше экспортированы именно из повторно открытого проекта,
не из PlantUML. Все восемь экспортов визуально просмотрены; независимое
семантическое ревью после исправлений — без блокирующих замечаний.
Водяные знаки evaluation edition сохранены.

Проверки не заменяют полный desktop-тест перетаскивания: проверены нормальный
режим подписей и сохранённая геометрия через Open API. Двенадцать тестов генератора
включают регрессии замечаний независимого ревью. Код приложения не изменялся;
базовые UC-2/UC-4 VPP, исходный проект пакетов и посторонние правки сохранены.

[sequences.xml](sequences.xml) — воспроизводимая спецификация генератора,
**не** замена VPP; [native-reopened.xml](native-reopened.xml) — нативный отчёт;
[source-manifest.json](source-manifest.json) — хэши исходных оснований.
[Инструменты](tools) используют Python standard library, Java compiler и VP;
это только документация, без новых runtime-зависимостей приложения.

Из Windows PowerShell, в **новый** выходной каталог:

```powershell
python -B -m unittest discover -s .\docs\architecture\uc-3\tools -p 'test_*.py'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\docs\architecture\uc-3\tools\Generate-Sequences.ps1 -Output "$env:TEMP\seasonplan-uc3-new"
python -B .\docs\architecture\uc-3\tools\validate_native.py .\docs\architecture\uc-3
```

Runner отказывается перезаписывать существующий VPP, работает с копией baseline,
проверяет его неизменность и удаляет собственный установленный плагин. Java-плагин
компилируется в release 11 для bundled VP JVM; target приложения остаётся Java 17.
