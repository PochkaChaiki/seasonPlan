## 2.2 User characteristics (Описание пользователей)

Система рассчитана на несколько типов пользователей с различным уровнем полномочий и частотой взаимодействия:

1. Фея-планировщик сезона: Опытный пользователь, отвечающий за создание сезонного плана. Работает с параметрами сезона, временными окнами, территориями и целевыми показателями. Инициирует сезон и анализирует его результаты.
    
2. Координатор талантов: Продвинутый пользователь, отвечающий за перевод плана в набор задач и назначений. Управляет составом участников, готовностью команд и ритуалом запуска.
    
3. Хранитель Древа Пыльцы / Хранитель пыльцы: Опытный или экспертный пользователь, управляющий ограниченным ресурсом пыльцы. Подтверждает резервы, отслеживает фактический расход, фиксирует дефицит и запрещает некорректный запуск сезона.
    
4. Балансировщик климата: Продвинутый пользователь, наблюдающий за показателями текущего сезона. Анализирует отклонения и инициирует корректирующие действия.
    
5. Контролёр магических аномалий: Опытный пользователь, отвечающий за ведение карточек инцидентов, их классификацию, эскалацию и закрытие.
    
6. Главный хранитель: Экспертный пользователь, принимающий финальные решения: утверждение плана, санкция запуска, принятие завершения сезона, перевод в аварийный режим и архивирование.
    
7. Исполнители-феи различных талантов: Обычные пользователи или ресурсы системы, задействованные в задачах и ритуалах. Их участие должно учитываться в назначениях и подтверждениях, но система не обязана хранить полный детализированный профиль каждой феи.
    

  

## 2.3 Assumptions and dependencies (Влияющие факторы и зависимости)

Предположения

- данные о природных метриках доступны системе либо автоматически, либо через ручной ввод; 
    
- данные о запасах пыльцы актуальны и корректны; 
    
- пользователи работают в рамках выделенных ролей; 
    
- сезонные правила и окна календаря определены и доступны; 
    
- инфраструктура Helios доступна для размещения разрабатываемого решения;
    
- в учебной версии допускается имитация части внешних интеграций. 
    

Зависимости

- от источников метрик и данных по пыльце; 
    
- от корректного ввода данных пользователями; 
    
- от полноты описанных бизнес-правил; 
    
- от доступности платформы и базы данных; 
    
- от точности ролевой модели; 
    
- от возможности реализации workflow, уведомлений и карточек.
    

## 2.4 Сonstraints (Ограничения)

На систему накладываются следующие ограничения:

- все ключевые процессы должны исполняться в рамках инфраструктуры Helios; 
    
- жизненный цикл SeasonPlan должен контролироваться через фиксированный набор статусов; 
    
- подтверждение сезона невозможно без одобренного резерва пыльцы; 
    
- запуск ритуала невозможен при наличии незакрытых критических блокировок; 
    
- AuditLog не должен допускать удаления или редактирования записей пользователем; 
    
- система должна поддерживать русский язык как основной язык интерфейса; 
    
- система должна учитывать, что пыльца является ограниченным ресурсом; 
    
- система не должна рассматриваться как симулятор мира фей. 
    

Границы модели

Система координирует сезон как операцию управления и контроля. Система:

- не моделирует индивидуальную биографию, внутреннее состояние или поведение каждой феи; 
    
- не симулирует природные и магические процессы на физическом уровне; 
    
- не обязана хранить полную историю низкоуровневых действий каждого исполнителя; 
    
- работает с агрегированными представлениями ресурсов, задач, метрик и инцидентов. 
    

Такой подход необходим, чтобы ограничить сложность решения, сделать систему реализуемой на Helios и сохранить фокус на бизнес-ценности автоматизации.

PR-6 Система должна поддерживать одновременную обработку не менее 100 событий (создание задач, инцидентов, обновлений) в минуту.

  

PR-7 Система должна обеспечивать загрузку основных экранов (дашборд, список задач, список инцидентов) не более чем за 3 секунды при нормальном сетевом соединении.

  

PR-8 Система должна обеспечивать корректную работу при увеличении объема данных за счет масштабирования (горизонтального или вертикального). 

  

3.5    Design Constraints (Ограничения разработки)

  

DC-1 Система должна быть реализована как веб-приложение с использованием клиент-серверной архитектуры.

  

DC-2 Система должна быть развёртываемой на сервере Helios.

  

DC-3 Серверная часть системы должна быть реализована на языке Java (OpenJDK 17 или выше).

  

DC-4 Клиентская часть должна быть реализована с использованием современных JavaScript-фреймворков (React.js).

  

DC-5 Система должна использовать PostgreSQL в качестве системы управления базами данных.

  

DC-6 Система должна использовать REST API для взаимодействия между клиентом и сервером.

  

DC-7 Все внешние взаимодействия должны осуществляться через HTTPS с использованием протокола TLS 1.2 или выше.

  

DC-8 Система должна использовать JSON в качестве формата обмена данными.

  

DC-9 Система должна поддерживать модель разграничения доступа RBAC (Role-Based Access Control).

  

DC-10 Система должна обеспечивать неизменяемость AuditLog на уровне базы данных.

  

DC-11 Система должна поддерживать возможность контейнеризации и развертывания с использованием Docker.

  

DC-12 Система должна обеспечивать интеграцию с внешними системами:

- Древо Пыльцы (REST API)

- Природный календарь (REST API)

- Система метрик (REST API / WebSocket)

  

DC-13 Система должна обеспечивать возможность имитации внешних интеграций в учебной версии проекта.

3.6     Interfaces (Интерфейсы)

3.6.1          User Interfaces (Пользовательские интерфейсы) 

Система должна предоставлять веб-интерфейс, доступный через браузеры (Google Chrome, Mozilla Firefox, Microsoft Edge).

Основные экраны:

1. Дашборд текущего сезона
    

- Отображение статуса сезона (DRAFT → ARCHIVED)
    
- Индикаторы критических рисков (красный/желтый/зеленый)
    
- Сводка по пыльце: запрошено / подтверждено / израсходовано
    
- Список активных инцидентов
    
- Список просроченных задач
    
- Ключевые метрики отклонений
    

3. Карточка SeasonPlan
    

- Форма создания/редактирования с валидацией полей
    
- Отображение истории изменений
    
- Блокировка полей в зависимости от статуса
    
- Кнопки действий (отправить, утвердить, запустить ритуал и т.д.)
    

5. Список задач (MagicTask)
    

- Таблица с фильтрацией по статусу, таланту, исполнителю
    
- Возможность групповых операций
    
- Детальный просмотр карточки задачи
    

7. Журнал инцидентов (MagicIncident)
    

- Карточки инцидентов с классификацией по тяжести
    
- Форма регистрации инцидента
    
- История обработки
    

9. Мониторинг ClimateMetric
    

- Графики изменения метрик по времени
    
- Отображение пороговых значений
    
- Визуализация deviation_score
    

11. Журнал аудита (AuditLog)
    

- Только чтение
    
- Фильтрация по дате, актеру, действию
    

13. Отчеты (SeasonReport)
    

- Просмотр сформированных отчетов
    
- Экспорт в PDF/HTML
    
- Сравнение с предыдущими сезонами
    

Требования к UI:

- Адаптивный дизайн для разрешений от 1366×768 до 1920×1080
    
- Поддержка русского языка интерфейса
    
- Время загрузки экрана не более 3 секунд (при нормальной сети)
    
- Валидация форм на клиенте с отображением понятных сообщений
    

  

3.6.2          Hardware Interfaces (Аппаратные интерфейсы)

  

Система использует следующую серверную и клиентскую инфраструктуру:

- Серверная часть размещается на сервере Helios (helios.cs.ifmo.ru) под управлением FreeBSD 14.4-STABLE, архитектура amd64
    
- Процессорная конфигурация сервера (hw.model): Intel(R) Xeon(R) CPU E5-2643 0 @ 3.30GHz, 16 логических ядер (hw.ncpu)
    
- Объем физической памяти сервера (hw.physmem) составляет 137381744640 байт (около 128 GB RAM)
    
- Системный раздел сервера имеет объем 456 GB
    
- Среда выполнения серверной части: OpenJDK 17.0.12.
    
- Доступ пользователей к системе осуществляется с рабочих станций и терминалов через веб-браузер по защищенному каналу HTTPS.
    
- Датчики природных метрик и внешние сервисы взаимодействуют с системой через программные интерфейсы API и не требуют прямого аппаратного подключения к клиентским устройствам.
    

  

Система взаимодействует со следующими аппаратными компонентами:

|Интерфейс|Назначение|Способ взаимодействия|
|---|---|---|
|Датчики природных метрик|Сбор показателей температуры, влажности, миграции|API через защищенный канал (HTTPS)|
|Магические кристаллы-терминалы|Обеспечение доступа фей к системе|Веб-интерфейс через браузер|
|Сервер Древа Пыльцы|Получение информации о запасах и резервирование|API через защищенный канал (HTTPS)|

3.6.3          Software Interfaces (Программные интерфейсы)

Система взаимодействует со следующими программными компонентами:

3.6.3.1 Внешние API

| Система                 | Тип интерфейса       | Назначение                                                       | Протокол |
| ----------------------- | -------------------- | ---------------------------------------------------------------- | -------- |
| Древо Пыльцы            | REST API             | Получение текущих запасов, резервирование, подтверждение расхода | HTTPS    |
| Природный Календарь     | REST API             | Получение правил сезонных окон, запретных территорий             | HTTPS    |
| Система датчиков метрик | REST API / WebSocket | Получение потоковых данных ClimateMetric                         | HTTPS    |

| Компонент           | Тип интерфейса   | Назначение                              |

| Система уведомлений | SMTP / WebSocket | Отправка уведомлений пользователям      |

3.6.3.3 Формат данных

Все API-запросы и ответы должны использовать формат JSON с кодировкой UTF-8.

  

3.6.4          Communications Interfaces (Сетевые интерфейсы)

3.6.4.1 Протоколы

- HTTPS (TLS 1.2+) – основной протокол для всех внешних взаимодействий
    
- HTTP/2 – рекомендуется для повышения производительности
    
- WebSocket –  для потоковой передачи ClimateMetric (опционально)
    

3.6.4.2 Сетевые требования

- Клиентская часть: доступ к серверу приложений через порт 443 (HTTPS)
    
- Серверная часть: доступ к базе данных через порт 5432 (PostgreSQL)
    
- Интеграции: доступ к API Древа Пыльцы и других внешних систем через порт 443
    

3.6.4.3 Безопасность сети

- Все внешние API-вызовы должны использовать взаимную аутентификацию (mTLS) или API-ключи
    
- AuditLog должен быть защищен от несанкционированного доступа на сетевом уровне
